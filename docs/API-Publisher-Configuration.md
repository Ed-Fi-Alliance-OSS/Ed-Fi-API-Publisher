# Ed-Fi API Publisher Configuration

The Ed-Fi API Publisher provides a hierarchical organization of configuration information, as documented below.

The first layer of configuration values are provided by the _publisherSettings.json_ file, which should reside in the same folder as the Ed-Fi API Publisher's binaries. This file contains the general Options available for altering the runtime behavior.
The Options values can also be supplied (overridden) using environment variables or command-line arguments, as needed.

Command-line arguments take precedence over environment variables, which in turn take precedence over the values defined in the _publisherSettings.json_ configuration file. To use environment variables to provide configuration values, use the "Configuration Path" from the tables below, and add an `EdFi:ApiPublisher:` prefix to the name of each variable. For example, to specify a named connection for the source API using an environment variable, use an environment variable name of `EdFi:ApiPublisher:Connections:Source:Name`.

### Bearer token handling

The publisher refreshes its bearer token while a run is in progress, and recovers when the API rejects a request as unauthorized by obtaining a new token and sending the request again.

- When the API reports the lifetime of the token it issues, the refresh interval is capped at half of that lifetime, so that the refresh always runs ahead of the expiry and a failed refresh can be retried before the token expires. This holds however short the lifetime is: an API issuing tokens that live less than a minute is refreshed every few seconds, and a warning is logged at startup pointing that out.
- A failed refresh is retried on a short, growing delay (5 seconds, doubling, capped at 60) for as long as the current token remains usable. Publishing is unaffected while that happens, because the token in hand is still valid. Once the token has expired, or when the API reports no lifetime, up to five consecutive failures are tolerated before the run ends.
- When the API rejects a request as unauthorized, the request waits while the token is re-acquired and is then sent again. If the token endpoint is unavailable at that moment, the re-acquisition is retried on the same backoff while the request waits, so a document or page is not lost to a brief outage of the token endpoint. A request body is buffered for that replay only once the request has been rejected, and only up to 16 MB; a larger body is not replayed and the unauthorized response is reported for it.
- When the token can no longer be obtained at all, the run ends with a `FATAL` log entry rather than continuing to send requests that the API will reject.

**Behavior change:** a run that cannot authenticate now exits with a non-zero exit code. Earlier versions could log the failure, keep going, and still exit `0`, so automation that treats a zero exit code as success will begin to see failures it previously did not.

### Reading from a busy source API

A source API that is serving other clients as well can answer a read with `429 Too Many Requests`, meaning the publisher is asking for more than the API is willing to serve at that moment. The publisher waits and sends the read again rather than recording it as a failure.

- The wait is taken from the `Retry-After` header the API returned, given either as a number of seconds or as the date the API will start answering again. That wait is a minimum: where the backoff for that attempt is longer, the longer of the two is used.
- Where the response carries no `Retry-After`, or carries one the publisher cannot read, the wait is the same exponential backoff used for other transient failures, starting at `RetryStartingDelayMilliseconds` and doubling with each attempt.
- The read is sent again up to `TooManyRequestsRetryAttempts` times, which follows `MaxRetryAttempts` unless it is set on its own. A read the API is still rejecting after that is reported as a failure, the same way a read that kept failing with `503 Service Unavailable` is reported today, so the run finishes with a non-empty error set and a non-zero exit code.
- This applies to reads from the source API only. A `429` returned by the target API in response to a POST is reported on the first response, unchanged from earlier versions. Bearer token requests are also outside this: they are sent on their own connection rather than through the request pipeline, so a `429` on a token request is not retried.

**Behavior change:** this is on by default. A read that previously failed within seconds of the source rejecting it is now waited out and retried, so a run against a busy source can take noticeably longer before it either succeeds or reports the same failure. Set `TooManyRequestsRetryAttempts` to `0` to return to the earlier behavior of reporting the rejection immediately. Do not use `MaxRetryAttempts` for this: that value drives every retry policy in the publisher, so setting it to `0` would also stop a source read being retried after a `503` and stop every retry on writes to the target.

**There is a ceiling on the wait, and it is the time one request has.** Each wait is spent inside the read that is waiting, against the 100 seconds a request is allowed in total, which is fixed and not configurable. Ten of those seconds are held back for the replay itself, so a wait of up to roughly 90 seconds is honored. A wait the remaining time cannot cover is not started at all: the read is abandoned and the rejection is reported straight away, with a log line naming the wait the API asked for and the time that was left. This is deliberate. Waiting anyway would let the request expire part-way through the wait, and the caller would then see a cancelled request with no status rather than the `429` that actually happened. So a source asking for two minutes gets a prompt, correctly labelled failure rather than a slow, mislabelled one.

One more thing worth knowing when sizing `MaxRetryAttempts`: this budget is spent inside a single request and is separate from the retry policy that covers other transient failures. A read that meets a `429` and then a `503` can spend both, so the worst-case number of attempts for one page is the product of the two rather than their sum. A retried read also does not pass back through the `EnableRateLimit` limiter, since the retry happens below it.

#### Capping what the source is asked to serve at once

`MaxConcurrentSourceRequests` is the other half of being a well-behaved client, and the two act at different points. Waiting out a `429` is a reaction to the source API having already been asked for too much; the cap keeps it from being asked in the first place. It counts requests to the source API as a whole, so it holds however the work happens to be divided between resources, and it is independent of `EnableRateLimit`, which limits requests per unit of time rather than requests at one time.

Two things the cap does not cover. Bearer token requests are not counted, for the same reason they are not retried. And a request holds its place only until the source has produced the response headers; the body is streamed after that, so a source can still be sending more than this many response bodies at once.

To pick a value, start from what the publisher can currently ask for at once, which is roughly `MaxDegreeOfParallelismForResourceProcessing` multiplied by `MaxDegreeOfParallelismForStreamResourcePages`, so 50 at the default settings, plus a few more for item counts and reference lookups. Halving that is a reasonable first step. Do not set it far below that product without also bringing the two parallelism settings down: a read waits for its place inside its own request, so if the queue is deep enough that reads at the back run out of the time a request is allowed, they are recorded as failures rather than simply served later. The publisher logs a warning at startup when the cap and the parallelism settings are that far apart.

### Backpressure and the memory ceiling

When the target API is slower than the source, the publisher's internal buffers are bounded so that source page fetching pauses instead of accumulating fetched items in memory without limit. `ProcessingBlockBoundedCapacity` controls this behavior:

- `0` (default) — automatic: the item buffer per resource-processing block is `max(StreamingPageSize, 4 × MaxDegreeOfParallelismForPostResourceItem)`.
- `-1` — disables all the buffering bounds (the memory-growth rollback lever; the compact error bodies and other memory improvements still apply).
- Any positive number — an explicit item capacity (values below `MaxDegreeOfParallelismForPostResourceItem` are raised to it so POST workers are never starved).
- Any other value fails options validation with a non-zero exit.

The same option governs the error publishing queue, so a sustained error storm also exerts backpressure instead of queueing errors in memory without limit. Each stage's errors pass through a tally block capped at `2 × ErrorPublishingBatchSize` (only one stage runs at a time), the shared ingestion queue is capped at another `2 × ErrorPublishingBatchSize` pending errors, and up to 4 more already-formed batches can be queued for publication behind it — a total of roughly `8 × ErrorPublishingBatchSize` pending errors (200 at shipped defaults), each of which can carry a full document body. All of them are unbounded under `-1`.

**What the ceiling actually is.** The capacity is per block, not a process-wide total. Page handling and item processing are joined by an item buffer of `itemCapacity` items: each page-fetch worker pushes items into it one at a time and pauses when it is full, so page fetching stops until the target catches up -- even when one page message expands into a whole partition of pages under cursor paging. Each live resource pipeline can therefore hold up to roughly `(MaxDegreeOfParallelismForStreamResourcePages × StreamingPageSize) + itemCapacity + itemCapacity` items across its buffers (one page per fetch worker being drained, the item buffer, and the processing block), and up to `MaxDegreeOfParallelismForResourceProcessing` resource pipelines stream concurrently. Delete and key-change pipelines chain two bounded item blocks, so their processing term is `2 × itemCapacity`. This is a fixed configuration-derived ceiling that does not grow with resource size or partition size. (One resource-proportional allocation remains: the per-resource list of page descriptors, which holds lightweight offset/limit entries or one partition token each.)

**Which settings actually lower the ceiling.** The dominant terms are one page per fetch worker (`MaxDegreeOfParallelismForStreamResourcePages × StreamingPageSize`) and the two item buffers (`2 × itemCapacity`, which defaults to `StreamingPageSize` when it is the larger value). For example, at `StreamingPageSize=500` and `MaxDegreeOfParallelismForStreamResourcePages=10`, up to 10 pages are being drained plus 1,000 buffered items -- 6,000 items per resource. To materially reduce per-resource retention, lower `MaxDegreeOfParallelismForStreamResourcePages` and/or `StreamingPageSize` (and `MaxDegreeOfParallelismForResourceProcessing` to reduce how many resources buffer concurrently); use `ProcessingBlockBoundedCapacity` to shrink or raise the item buffers, or to disable bounding entirely.

**Streamed page reads.** When streaming from an API source, a fetched page is no longer buffered as a whole string before item splitting — the response body is parsed in a single forward-only pass that materializes one document at a time, so the per-page memory constant inside the ceiling above is one document rather than one whole page of text (see APIPUB-134). The SQLite connector is the documented exception: as a target it stores whole pages as TEXT rows, so it deliberately buffers each page string before writing it.

**Cursor paging.** Against an ODS/API 7.3+ source each page message is a partition rather than a single page. Partitions are walked page by page and every page is delivered through the bounded item buffer before the next one is fetched, so the ceiling above applies unchanged; `--disableCursorPaging=true` restores the offset/limit path with the same bound.

**Operational notes.** Slower or paused source page fetching while the target catches up is the bound working as intended, not a hang — the log reports the resolved capacities (items, page messages, pending errors) at startup. Resources configured for authorization-failure retry in `authorizationFailureHandling` are re-streamed through a retry pipeline after their update prerequisites complete; that second pass is bounded exactly like any other pipeline, so the ceiling above applies to it as well.

### Run outcome and exit codes

**Behavior change:** every failure previously returned a single exit code of `-1` (surfaced as `255` on Linux and macOS). Failures now return the specific codes below, and a rate limit rejection, which used to be logged and abandoned, now fails the run. A caller that tests for a non-zero exit code is unaffected; a caller that tests for `255` or `-1` specifically must be updated, and a scheduled job that was silently tolerating rate-limited losses will start reporting them.

A run reports its outcome through its exit code, so that an unattended or scheduled publish does not need the log to tell a complete run from one that lost documents:

| Exit code | Meaning | Expected response |
| --------- | ------- | ----------------- |
| `0` | Everything the run set out to publish was published, or the documents that failed were within `ToleratedItemErrorCount`. | None. |
| `1` | Every resource ran to completion, but documents were rejected by the target beyond the configured tolerance. | Read the run summary and the published errors, correct the data or the target, and re-publish. |
| `2` | The run did not complete, or part of the source could not be read: a resource faulted or was cancelled, a page or an item count could not be retrieved, the errors themselves could not be published, or a finalization activity failed. What was published is unknown. | Re-run. |
| `3` | The publisher could not authenticate against the source or target API. | Correct the credentials. |
| `4` | The configuration or the supplied options are invalid, so no publishing was attempted. | Correct the configuration. |

Every run also prints a summary table, on both the success and the failure paths, reporting per resource and stage what the source reported (`Expected`), how many documents were read from the source and handed to the target (`Attempted`), how many the target rejected (`Failed`), how many were abandoned without being published or rejected (`Skipped`), and how many the target holds as the source asked (`Published`). Every one of those is counted where it happens, so a run that stopped with documents in flight reports them as attempted and nothing else, and says how many below the table. `Published` includes the documents that needed no write because the target already satisfied them: a descriptor whose value is already present, a deleted document the target no longer has, and a key change whose item is not on the target. Those cost nothing and lose nothing, so they do not hold the change version back. Errors reading the source (a page or an item count that could not be retrieved) are reported below the table instead of against a resource, because the documents behind them were never attempted and their number is not known.

A resource listed in `authorizationFailureHandling` is published twice: once by the pass that reads it, and again by the authorization retry pass once its update prerequisites complete. The row reports the second pass, because it republishes every document of the resource and therefore decides what the target holds, and a line below the table gives what the first pass had reported and how much the retry recovered. A document rejected on both passes is one failed document, not two.

Counts are in documents on every connection. The SQLite target is the one that writes a page at a time rather than a document at a time, so its pages report the number of documents they carry; a page that could not be written counts as every document in it.

**Best-effort publishing does not advance the last change version processed.** A run that reported an error for any document never records a new last change version, even when `ToleratedItemErrorCount` allowed it to report success. The one exception is a document you have chosen to abandon: a resource ignored through `treatForbiddenPostAsWarning` is reported in the summary's `Skipped` column and does not hold the change version back, because abandoning it was the configured intent. The documents that failed are inside the change window that was just published, so re-publishing that window on the next run is what gives them another chance; advancing the change version past them would leave them unrecoverable without a full re-publish. The consequence to plan for is the opposite one: while documents keep failing for a reason that does not go away, an incremental run keeps re-publishing the same window, which grows as the source changes. Best-effort makes the exit code quiet, not the loss.

## API Connections

Metadata for source and targets API connections can be supplied to the publisher using values stored in a persistent configuration or through environment variables and/or command-line arguments, as documented below. It is **strongly recommended** that you use named connections with persistent configuration for repeated publishing operations (e.g. `--sourceName=abcd --targetName=wxyz`). You should not mix named connections with overrides supplied through environment variables or command-line arguments.

> NOTE: If the Ed-Fi API Publisher is executed using explicit connection information (rather than a pre-configured _named_ connection), the LastChangeVersionProcessed value cannot be updated automatically upon successful publishing (as there is no API connection name associated with the information). It will be the responsibility of the caller to update the value appropriately after extracting the new change version from the log output (or through some other enterprising manner). As such, for implementing a process that is intended to only publish _changes_ from a source to a target, it is impractical to use an approach where the API connection details are provided explicitly at execution time.

## Considerations in relation to key changes and deletes

Ed-Fi API Publisher will only process key changes and deletions if  specific Change Window is defined. To do so use the
`--lastChangeVersionProcessed` value and set the `--useChangeVersionPaging` flag to true.
Another option, if you want to keep the `--useChangeVersionPaging` false is defining a name for the source and target, using the
`--sourceName` and `--targetName` values. More information about all these values [below](API-Publisher-Configuration.md#api-connections).

When performing a full publish (change window starting at version 1 or below), delete and key change processing are skipped by default. Use `--processDeletesAndKeyChangesOnFullPublish=true` if you need these operations to run during a full publish.

## Authorization Failure Handling

Defines metadata (as an array of JSON objects) about which resources could experience `403 Forbidden` responses caused by data dependencies needed for successful authorization, and which other resources should be processed before retrying the original request. For example, while an API client may be able to create a Student, they won't be able to _update_ the Student until that Student is enrolled in a School through the StudentSchoolAssociation. By defining the authorization-related dependency of the _update_ operation on the StudentSchoolAssociation, the Ed-Fi API Publisher can know to retry the failed POST request after the association has been established.

NOTE: This part of the configuration can only be defined in the _publisherSettings.json_ file.

| JSON Path                                                  | Description                                                                                                                                                                                                  |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| /authorizationFailureHandling\[\*]                         | Defines metadata for a single resource which could experience 403 Forbidden responses.                                                                                                                       |
| /authorizationFailureHandling\[\*]/path                    | The partial path for the resource (e.g. _/ed-fi/students_) for which additional 403 Forbidden processing should be performed.                                                                                |
| /authorizationFailureHandling\[\*]/updatePrerequisitePaths | An array of partial paths for the resource(s) (e.g. _/ed-fi/studentSchoolAssociations_) that should be processed before attempting to retry the original request which resulted in an authorization failure. |

The default configuration targets Data Standard 5.x and later, where the parent resource is `/ed-fi/contacts`. For sources on Data Standard 4.0 or earlier, replace that entry with `/ed-fi/parents` → `/ed-fi/studentParentAssociations`. An entry whose path or prerequisites do not exist in the source's dependency graph is skipped with a warning in the log (it does not fail the run).

How the retry works: a `403 Forbidden` POST response for a configured resource is skipped without publishing an error, because the entire resource is re-published through a second, bounded streaming pass once all of its `updatePrerequisitePaths` resources have completed. Individual failed items are not queued or retried in place — the second pass covers them (which also means the resource's documents are fetched from the source and sent to the target twice). A request that is still `Forbidden` during the second pass is treated as a final error (or as a warning, when the target connection sets `treatForbiddenPostAsWarning`).

The default configuration is as follows:
```json
{  
  "options":   
  {  
    ...
  },  
  "authorizationFailureHandling": [  
    {  
      "path": "/ed-fi/students",  
      "updatePrerequisitePaths": ["/ed-fi/studentSchoolAssociations"]  
    },  
    {  
      "path": "/ed-fi/staffs",  
      "updatePrerequisitePaths": [  
        "/ed-fi/staffEducationOrganizationEmploymentAssociations",  
        "/ed-fi/staffEducationOrganizationAssignmentAssociations"  
      ]  
    },  
    {  
      "path": "/ed-fi/contacts",  
      "updatePrerequisitePaths": ["/ed-fi/studentContactAssociations"]  
    }
  ]
}
```
